# Daybook for iPhone

The iPhone app: everything the Mac app does except run models (see docs/iphone.md). Phase 1 is the
shell: the Xcode project, the recording engine, the Live Activity, controls, widgets, and App
Intents, plus a minimal interface to drive them.

## Building

`Apps/iOS/project.yml` is the source of truth. `Daybook.xcodeproj` is generated by XcodeGen and
ignored by git, so it never conflicts; regenerate it whenever the spec or the file list changes.

```sh
brew install xcodegen                     # once
scripts/build-ios.sh                      # generate, then build for the iOS Simulator
scripts/build-ios.sh --test               # ... and run the unit tests (an iPhone Duo simulator if there is one)
scripts/build-ios.sh --generate-only      # just regenerate, then open Apps/iOS/Daybook.xcodeproj
scripts/build-ios.sh --device             # a signed build for a physical iPhone (never installs it)
scripts/build-ios.sh --device --no-sign   # compile for a device without signing
```

The script copies the repository's `Package.resolved` into the generated project, so Xcode resolves
the same package versions as `swift build`.

Requirements: Xcode with the iOS 27.1 SDK (the hinge APIs), XcodeGen. The app runs on iOS 26.0 and
later; the hinge features turn on with iOS 27.1.

### Signing and iCloud

Automatic signing; the team comes from `DAYBOOK_TEAM_ID` through `Config/Signing.xcconfig`. From the
command line, export it. From Xcode, which doesn't see shell variables, create
`Config/Signing.local.xcconfig` (ignored by git) with `DAYBOOK_TEAM_ID = ABCDE12345`. Simulator
builds need no team.

Identifiers: `local.daybook.phone` (app), `local.daybook.phone.widgets` (widget extension), app group
`group.local.daybook.phone`, iCloud container `$(DAYBOOK_ICLOUD_CONTAINER)` (default
`iCloud.local.daybook`, set in `Config/Signing.xcconfig` and overridable in the local file).

Sync uses the app's own iCloud ubiquity container, not a folder picked in Files. The app's
entitlements carry `com.apple.developer.icloud-services = [CloudDocuments, CloudKit]` and the container in
`icloud-container-identifiers` and `ubiquity-container-identifiers`, plus `aps-environment`
(`$(DAYBOOK_APS_ENVIRONMENT)`, `development`; the App Store export re-signs it `production`). CloudKit and
push carry the courier, which sends each recording to the Mac ahead of iCloud Drive (docs/icloud-sync.md,
"Courier (CloudKit)"); the app never creates it in tests or with `--sync-folder`. Info.plist's
`DaybookICloudContainerIdentifier` names it for `LibrarySyncController`, which resolves
`url(forUbiquityContainerIdentifier:)/Documents/Daybook`. There's no `NSUbiquitousContainers` entry,
so the container stays out of the Files app. Without a team, or without iCloud Drive, the app says
"iCloud isn't available" and keeps recordings on the phone.

Registering the identifiers, app group, iCloud container, CloudKit, and Push Notifications on the Apple
Developer account is a separate, deliberate step for the account owner (docs/release.md, "One-time setup").
Nothing here does it: the build script never passes `-allowProvisioningUpdates`.

## Layout

| Folder | What's in it |
|---|---|
| `DaybookPhone/Recording` | `PhoneRecorder` and its parts: audio session, inputs (microphone and synthetic), the AAC segment writer, the crash journal, the assembler that joins segments |
| `DaybookPhone/Recording` (UI) | `RecordingSurface` in the pocket, notebook, and table postures, `RecordStartButton`, recording-only tokens (`RecordingStyle`) |
| `DaybookPhone/Library` | `PhoneLibrary` (DaybookKit's `LibraryController`, filing, imports), `SyncAudioProvider` (audio on demand), `CloudAvailability` |
| `DaybookPhone/Link` | `PhoneLink`, the DaybookLink client: pairing, connections, live progress, record control; Settings › Macs and pairing |
| `DaybookPhone/Devices` | `PhoneDevices`, DaybookDevices on iPhone (Soundcore with background Bluetooth and state restoration), the recorder handoff (`handoff`, DaybookKit's `RecorderHandoff`); recorder screens and `RecorderHandoffCard` |
| `DaybookPhone/Status` | The status sheet (pocket) and panel (notebook): `StatusSheetModel` (the words, tested), `StatusSheet` (the views), and `LiveCaptionsFallback` (delete when `DeviceSession.liveCaptions` lands) |
| `DaybookPhone/Settings` | `SettingsScreen`: iCloud, Macs, recorders, recording, storage, templates, vocabulary, About |
| `DaybookPhone/Posture` | `DevicePosture` (closed, partly open, open, angle) fed by `onHingeChange` |
| `DaybookPhone/App` | the app model that ties recorder, library, sync (`PhoneSync`), the link, recorders, Live Activity, and widgets together; `MacPresence`, `LiveProgress`, multipoint; launch options; Siri phrases |
| `DaybookPhone/UI` | the shell's interface |
| `DaybookPhoneWidgets` | the Live Activity and Dynamic Island, the Control Center control, the Recorder widget |
| `Shared` | compiled into both app and extension: App Intents, Live Activity attributes, the app-group state, design tokens |
| `DaybookPhoneTests` | XCTest, hosted in the app |
| `Tools/duo-fold` | folds and unfolds an iPhone Duo simulator from the command line (simulator-only, private SpringBoard SPI) |

App Intents are a shared source group rather than a framework: each target compiles them, so each
bundle's intent metadata lists what its surfaces use, with no framework to embed or
`AppIntentsPackage` to maintain. The recording intents conform to `AudioRecordingIntent` or
`LiveActivityIntent`, so the system always performs them in the app's process, where the recorder is.

## Services for the interface

The app model (`PhoneAppModel`, in the environment) exposes what the library and reading screens
need from sync and the link. All are `@Observable`, so views update as they change.

| API | What it is |
| --- | --- |
| `model.macPresence` | `MacPresence`: `.connected(name:)` (a paired Mac that transcribes is on the link now), `.seen(name:lastSeen:)` (its last sync, from presence records), `.olderMac`, `.noMac`, `.unavailable(reason)`, `.checking`. `waitingLine()` is the line under a conversation whose `ProcessingStatus` is `.requested(.device)`: "Waiting for Studio Mac", "Waiting for your Mac · last seen 2 h ago", "No Mac has synced this library yet". `summary()` is a sentence for Settings. |
| `model.liveProgress[meetingID]` | `LiveProgress` from a connected Mac (`processing.progress`): `phase`, `fraction`, `macName`, `detail`, and `line` ("Transcribing on Studio Mac · 40%"). Prefer it over a claim's coarse synced progress while present. Entries clear when the Mac finishes (a sync pass then brings the result) or after two minutes without word. |
| `\.audioProvider` (and `model.audio`) | `SyncAudioProvider`, the sync-backed `AudioProviding`: `localAudio(for:in:progress:)` makes a track local (downloading from iCloud with progress; cancel the task to stop; nothing partial is left), `availability(of:in:)` says `.local`, `.inCloud`, or `.unavailable(reason)`. `downloads[trackID]` holds the fraction of downloads in flight; call `notePlayed(_:in:)` while playing so eviction keeps it. Settings › Storage sets the budget and clears downloads. |
| `model.processingLine(for: meeting)` | The one honest processing line for a conversation, or nil: live progress, else the synced claim ("Transcribing on Studio Mac · 40%"), a waiting request with the Mac's presence and, when the link knows, why it's busy ("Waiting for Studio Mac, which is recording"), "Not transcribed yet", or the Mac's failure. |
| `model.sync` | `PhoneSync`: `statusLine` ("Up to date", "Syncing 3 changes", "iCloud isn't available, so …"), `detailLine()`, `devices` (presence), `lastReceived`, `synchronize(_:)`. |
| `model.multipoint`, `model.multipointLine` | A recording made with a Mac: "Also recording on Studio Mac" or "Recording with Studio Mac". |
| `model.devices.handoff` | `RecorderHandoff`: `state(of:)` for a recorder (asking, the Mac finishing an import, waiting through iCloud, refused, connecting, done), `useHere`, `takeOverAnyway`, `give(_:to:)`, `peersToGive`; `RecorderHandoff.Words` has the lines. `PhoneDevices.useHere`/`give`/`handoffState` wrap it for Observation. |
| `\.statusSheetInset` | Set while the status sheet holds Record at the foot of the pocket library: the room to leave above it. |

`App/AudioProvidingShim.swift` defines `AudioProviding` and `\.audioProvider` until the reading work's
`Reading/Playback/` lands; delete the shim then.

Sync cadence on the phone: a pass on launch, on returning to the foreground, right after a recording or
import is filed (under a background-task assertion, so the upload starts even if the app is then
closed), and two seconds after an edit; while running, a listing-only check every 30 seconds; in the
background, `BGAppRefreshTask` (`local.daybook.phone.sync`) with `.background` limits. Passes are
bounded and continue a second later while there's more to read.

## Live captions and flex mode

While recording, tentative captions made on this iPhone show that it's hearing the conversation
(`Captions/`, on the shared `DaybookCaptions` engine: `SpeechAnalyzer` + `SpeechTranscriber` with
volatile and fast results). They're never the transcript: they're saved phone-locally in
`<library>/LiveCaptions/<meeting>.json` (`LiveCaptionStore`, outside what syncs), tied to the phone
track once filed, hidden once a Mac's transcript exists (`Meeting.showsLiveCaptions`), and removed
with the conversation. The captioner is fed from the recorder's tap, drops audio when behind, and
can't stop a recording. Settings › Recording turns them on and picks the language; a language needs
a system download (`AssetInventory`) the first time it's used, which starts only when recording.
The simulator has no `SpeechTranscriber` (`isAvailable` is false), so `--demo-captions` scripts them
for screenshots and `--caption-probe` records what the device supports.

Table mode follows how the Duo stands: like a book (hinge vertical) it splits left and right; turned a
quarter turn like a laptop (flex mode, hinge across) it splits at the horizontal crease, with captions,
the clock, and the level on the standing half and Bookmark and Stop on the flat half
(`HorizontalCreaseSplit`). The simulator can't turn the device (`requestGeometryUpdate` is refused on
the inner display), so `--interface-orientation preview-portrait` draws flex mode turned inside the
landscape window for screenshots.

## Checking it in the simulator without a microphone

Debug builds accept launch arguments (see `DaybookPhone/App/LaunchOptions.swift`). With
`--synthetic-audio` the recorder records generated speech and never opens an audio session, so the
simulator never routes the Mac's microphone:

```sh
xcrun simctl launch <udid> local.daybook.phone --synthetic-audio --start-recording --demo-notes
xcrun simctl launch <udid> local.daybook.phone --posture open        # or closed, partial[:degrees]
xcrun simctl launch <udid> local.daybook.phone --log-geometry        # window, safe area, posture to Documents/geometry.jsonl
xcrun simctl launch <udid> local.daybook.phone --open-latest         # the newest conversation's page
xcrun simctl launch <udid> local.daybook.phone --synthetic-audio --start-recording --simulate-interruption 6   # paused for a call
xcrun simctl launch <udid> local.daybook.phone --synthetic-audio --start-recording --demo-multipoint "Studio Mac"
xcrun simctl launch <udid> local.daybook.phone --demo-link --open-settings              # Settings; also macs, pairing, storage, …
xcrun simctl launch <udid> local.daybook.phone --sync-folder /tmp/container --demo-mac "Studio Mac:2"   # sync through a folder
xcrun simctl launch <udid> local.daybook.phone --device-simulator --device-autopilot --open-settings device   # Soundcore, simulated
xcrun simctl launch <udid> local.daybook.phone --synthetic-audio --start-recording --demo-notes --demo-captions  # scripted captions
xcrun simctl launch <udid> local.daybook.phone --synthetic-audio --start-recording --demo-notes --posture partial --interface-orientation preview-portrait --write-notes   # table mode, writing (fold to book first)
xcrun simctl launch <udid> local.daybook.phone --caption-probe /path/to/audio.m4a   # Documents/caption-probe.json; never downloads
xcrun simctl launch <udid> local.daybook.phone --device-simulator --device-autopilot --demo-link --status-detent medium   # the status sheet (or panel) at a size
xcrun simctl launch <udid> local.daybook.phone --device-simulator --device-autopilot --demo-link --handoff-demo waiting --open-settings device   # a handoff state
xcrun simctl launch <udid> local.daybook.phone --device-simulator --device-autopilot --demo-link --demo-live-captions --status-detent medium   # captions while the recorder streams
xcrun simctl launch <udid> local.daybook.phone --library <dir> --demo-library --speaker-demo --select "Vendor call" --sheet info --info-detent large --info-scroll people   # Recognized and Maybe
xcrun simctl launch <udid> local.daybook.phone --library <dir> --open-settings speaker-profile:Vladimir --profile-name Vlad   # a profile; also --merge-into Vlad [--confirm-merge]
Apps/iOS/Tools/duo-fold/duo-fold.sh <udid> open                      # or closed, book, 0.0–1.0
```

The iPhone Duo's measured displays, safe areas, and hinge behaviour are in docs/iphone.md
(iPhone Duo › Measured).
